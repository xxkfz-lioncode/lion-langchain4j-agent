# RAG 知识库：现状梳理与企业级差距清单

> 更新时间: 2026-11
> 对照对象: 企业级生产产品(Dify / RAGFlow / 阿里云百炼一类)
> 用途: 迭代规划参考, 按优先级排列; 已完成项会随迭代更新状态

---

## 一、当前已具备的能力

### 架构底子

```
上传(仅保存) → 解析(异步: 切分+向量化) → 问答(检索+引用溯源)
     │              │                        │
  FileStorage   RagParseWorker          EmbeddingStore 直接检索
  (local/minio) (独立线程池+进度回写)      (Top-N + minScore + 相似度分数)
```

| 能力 | 说明 | 状态 |
|---|---|---|
| 两阶段上传/解析 | 上传只保存文件, 解析显式触发(可先选切分方式) | ✅ |
| 异步解析 + 进度 | @Async 独立线程池, 进度 0-100 实时回写, 前端轮询展示"解析中 xx%" | ✅ |
| 解析状态机 | 0 待解析 / 1 已解析 / 2 解析中 / 3 解析失败, 失败原因落库(error_msg)可重试 | ✅ |
| 存储抽象 | FileStorage 接口双实现(本地磁盘 / MinIO), 存量文件按 storage_type 路由共存 | ✅ |
| 7 种切分方式 | recursive/paragraph/sentence/line/word/character/regex, 参数可自定义并持久化 | ✅ |
| 引用溯源(方案一) | 回答携带引用来源(文档名/匹配度/片段摘要), 检索层注入, 与提示词片段一一对应 | ✅ |
| 引用页码定位 | PDF 按页解析(PDFBox 逐页拆分), 片段携带页码, 引用条显示"第 N 页" | ✅ |
| 原文下载 | 管理页下载按钮, 按 storage_type 路由, RFC 5987 中文文件名 | ✅ |
| Milvus 向量库 | 片段元数据带 docId/fileName, 按文档精确删除 | ✅ |

### 已有但偏基础

| 能力 | 现状 | 与生产的差距 |
|---|---|---|
| 流式回答 | 对话助手页有真流式; 知识问答是阻塞返回+前端假打字机 | 见 P0-2 |
| 引用展示 | 只有文档名+分数+摘要, 点开看全文 | 见 P0-4 |

## 二、差距清单(按优先级)

### P0 —— 生产必须, 当前缺失

| # | 缺口 | 现状 | 生产做法 | 预估改动 |
|---|---|---|---|---|
| 1 | ~~异步解析 + 进度反馈~~ | — | 任务表/队列 + 状态机 + 轮询/SSE 推进度 | **已完成** |
| 2 | **SSE 流式回答** | `/api/rag/chat` 阻塞整段返回, 前端打字机是"假流式" | 对话助手页已有真流式, 知识问答应对齐(SSE + 逐 token), 引用来源在流结束帧下发 | 中 |
| 3 | ~~失败可观测~~ | — | error_msg/retry_count/parse_time 落库 + 管理页展示 | **已完成** |
| 4 | ~~引用定位粒度(页码)~~ | — | PDF 按页解析, 页码随片段入库, 引用显示"第 N 页" | **已完成**(章节标题进阶版暂缓) |

### P1 —— 生产竞争力, 影响效果上限

| # | 缺口 | 说明 |
|---|---|---|
| 5 | ~~Rerank 重排~~ | **已完成**: DashScope gte-rerank-v2 交叉编码器, 混合检索融合候选逐对打分取 Top5; 失败/关闭自动降级融合排序(lion.rag.rerank.* 可配) |
| 6 | ~~混合检索~~ | **已完成**: 向量(Top20/0.6) + BM25(rag_segment 表 + 应用内存打分, 中文 bigram 分词) 双路召回 → RRF 融合; 生产规模化可换 ES/Milvus sparse, 链路不变 |
| 7 | **多知识库** | 当前全系统一个库。生产必须有 KB 实体(建库/删库/按库上传问答) + 库级 RBAC 权限 + 库级隔离(Milvus partition 或 collection)。大工程, 涉及表结构/路由/权限全链路 |
| 8 | **更多文件格式** | 只支持 txt/md/pdf。企业真实语料: docx/xlsx/ppt/html/邮件/图片扫描件(OCR)。生产用 Tika 或 Unstructured 统一解析 |
| 9 | **分段预览** | 点文档能看到切出来的片段长什么样——调切分策略必备的调试视图 |
| 10 | **重复上传/版本** | 同名文件再上传会生成重复文档。生产做内容 hash 去重 + 文档版本替换(新版本入库自动清旧向量) |

### P2 —— 规模化后才必要

| # | 缺口 | 说明 |
|---|---|---|
| 11 | **评测体系** | golden QA 集合 + RAGAS 指标(召回率/忠实度); 改切分参数、换 embedding 模型前先跑评测, 而不是肉眼感觉 |
| 12 | **反馈闭环** | 回答点赞/点踩 + 负反馈回流成待修数据 |
| 13 | **可观测/审计** | 检索命中日志(谁问了什么、命中哪些片段)、token 成本统计、tracing(Langfuse) |
| 14 | **安全** | 上传文件病毒扫描、内容审核、**引用权限校验**(多租户后: 用户 A 的提问不能带出用户 B 无权文档的片段, 硬要求) |
| 15 | **向量库运维** | 换 embedding 模型后的全量重建工具、DB 与向量库的定期对账任务 |
| 16 | **性能** | embedding 并发限流池、热门问题缓存、大文件分片上传/断点续传 |

## 三、建议迭代路线

```
已走完:  存储抽象 → 引用溯源 → 异步解析+状态机+失败可观测 → 引用页码定位
        → 混合检索+Rerank 精排(生产标准召回链路: 双路召回 → RRF → 交叉精排)
下一步:  SSE 流式回答(P0-2) —— 对话体验对齐, 复用助手页已有流式基建
之后:    多知识库(P1-7) 作为独立大迭代
```

选择依据:

- **①②③ 改动都可控**(一两天级), 且分别解决"体验/效果/溯源"三个维度的最短板
- 多知识库是表结构级改造, 期间会冻结其他 RAG 需求, 宜单独立项
- P2 项在用户量/文档量上来之前投入产出比低, 记录在案即可

## 四、已知的技术债(小, 记录在案)

| 事项 | 说明 |
|---|---|
| DB 与向量库可能不一致 | 删向量时 Milvus 挂了只 warn 不阻断, DB 汇总可能偏多; 重解析即修复。对账任务见 P2-15 |
| 匹配度阈值写死在后端常量 | `MIN_SCORE=0.75`, 换 embedding 模型/语料后需要重新标定; 生产应做成配置项 |
| 解析线程池参数经验值 | core 2 / max 4 / queue 100, 按 DashScope 限流保守设定; 生产应结合配额压测调整 |
