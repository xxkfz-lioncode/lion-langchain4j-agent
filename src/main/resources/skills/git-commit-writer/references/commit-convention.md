# Commit Message 约定

## 1. 基本结构

```
<type>(<scope>): <subject>

<body>

<footer>
```

- **subject**：动词开头的一句话概括，说明「做了什么」，中文或英文与仓库既有风格一致；句末不加句号，尽量 ≤ 50 字符。
- **body**：说明「为什么改 / 关键实现点 / 影响面」，用 `-` 列表；不复述 diff 的逐行细节。
- **footer**：仅在存在 BREAKING CHANGE（`BREAKING CHANGE: ...`）或用户提供了 issue / PR 编号时书写；**禁止编造**编号。

## 2. type 取值

| type | 用途 |
| --- | --- |
| `feat` | 新功能、新接口、新页面 |
| `fix` | 缺陷修复 |
| `refactor` | 重构（不改变外部行为） |
| `perf` | 性能优化 |
| `docs` | 文档、注释、README |
| `style` | 格式、命名、空行等不影响逻辑的调整 |
| `test` | 测试用例 |
| `build` | 构建脚本、依赖版本（pom / package.json / Dockerfile） |
| `ci` | CI 流水线配置 |
| `chore` | 杂项（配置、脚本、清理） |
| `revert` | 回滚某次提交 |

`scope` 可选，用于限定模块，例如 `feat(knowledge):`、`fix(chat):`。仓库既有提交若不用 scope，不要强行添加。

## 3. 多主题提交（一个 commit 含多个独立改动）

当一次改动包含多个互相独立、又一起提交的主题时，用编号子项组织，参考：

```
feat: 新增 PDF 按页切分策略，知识库向量配置独立化并完善文档预览

1) feat: 知识库文档切分新增「按页切分（PDF）」
- 新增 PageSplitterStrategy：按页提取、页边距裁页眉页脚
- 切分策略接口新增解析型扩展点，块透传页码元数据供引用溯源
- 前端上传页新增切分方式下拉并记忆上次选择

2) refactor: 知识库向量配置解耦为独立配置项
- 入库侧不再直接读取向量库自动配置前缀

3) docs: README 补充项目效果图与核心设计章节
```

## 4. 何时建议拆分提交

- 所有改动可用一句话概括、彼此存在依赖 → 输出**单个**提交信息。
- 主题彼此独立（如「新增功能」+「基础设施重构」+「文档」）→ 给出**多条** message，每条对应一组文件，并说明建议的 `git add <path>` 分组。
- 只输出文本，不自动执行 `git add` / `git commit`，除非用户明确要求提交。
- 若仓库中已存在暂存区，默认以暂存区内容为提交范围；暂存区为空时提醒用户，并给出建议的 add 命令。

## 5. 与仓库历史风格对齐（优先）

生成前先看 `collect_changes.py` 输出的「最近提交风格」小节：

- 历史提交为中文 + `feat:` 前缀 → 保持中文与相同前缀；
- 历史提交使用 `1) 2)` 多主题结构 → 沿用该结构；
- 历史提交为英文 Conventional Commits → 用英文；
- 当历史风格与本文档冲突时，**以仓库历史风格为准**。

## 6. 反例（避免）

- ❌ `update` / `修改代码` / `提交` / `fix bug` —— 无信息量。
- ❌ 把 diff 逐行翻译成 body（例如「第 12 行增加了 null 判断」）。
- ❌ 虚构 issue / PR / 评审人信息。
- ❌ subject 过长、带句号、同时包含多个互不相关主题。
- ❌ 使用 `git commit --amend`、`--no-verify` 等需要用户明确授权的操作。
